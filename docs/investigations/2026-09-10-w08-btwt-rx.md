# W-08 广播 TWT 收包长度、响应关联与保护布局

本批将广播响应绑定到 TX 完成后仍有效的 response timer，并修正上一批 TX
对广播帧长度/保护布局的不完整假设。公开 setup/close、托管 Agreement、RF
晚到帧在 dialog 重用后的隔离及完整联合回收仍未完成。

## 从固定 SDK 重新确认的事实

SDK `fff9895c82`：he_send_action_twt_setup 分配/复制 20 B，但广播分支在
+0x12c 将实际发送末尾增加 15 B。广播 IE 长度字段为 10，总 IE 为 12 B；
action category/action/dialog 共 3 B。上一批要求至少 20 B 会错误拒绝正常
广播发送，本批改为读取 15 B 并只保存有效的 12 B IE，后五字节归零。

同一 builder 会选择 robust management frame，设置保护标志，并将 category/
action 改成 23/4。原广播完成 callback 仍固定用 24-byte MAC header，未像
individual 分支那样处理保护头偏移；因此不能以拒绝保护帧作为最终支持方案。

STA 调用 parse_action 后将 node、MAC header、body、one-past-end 四个参数
传给 recv_action；dispatcher 和注册的 TWT handler 保留它们。parse_action
没有为 TWT 保证完整 payload，原 he_recv_action_twt_setup 在检查长度前读
body[5]；广播分支随后仅凭 ID 删除 timer，并从 body+3 固定复制 17 B。
这些为归档反汇编和生产源代码证据，没有写成动态复现或实机通过。

## 生产处理

1. 已注册的 TWT 收包函数指针改为 framework wrapper。先检查 body/end 的
   顺序和最小长度，再检查 category/action、IE ID 和声明长度。广播至少 15 B；
   individual 至少 20 B 后才进入原 handler。
2. 广播收包复制 15 B 到补零的 20 B 栈副本；原 SDK 后续 17 B 参数复制始终
   有效，既不读取短帧之外的存储，也不把跟随 IE/分配尾部当成请求参数。
3. 发送完成从实际 PMF/非 PMF body 读取有效字段，只把值传给 SDK adapter。
   adapter 为原广播 callback 构造同步、对齐的固定 ABI 输入：descriptor、
   frame、metadata/status；原 callback 只读取它并复制到原生 timer 存储，不
   保留或回收该输入。真实 driver EB 不改写，原生加密/PMF 策略不改变。
4. 成功 TX 安装 response timer 后，将 echoed dialog 绑定到匹配 node/参数
   的精确 timer identity。RX 必须匹配当前关联、dialog、response phase，
   且 timer 尚未触发或消费；不匹配的帧不清理/改写任何 timer。
5. 先消费一次响应权限并尝试旧 timer stop/delete。清理失败则保存原生错误，
   不调用会替换参数的 SDK RX。REJECT/ALTERNATE/DICTATE 的原生观察被捕获，
   处理返回后保存终态并零等待发布。ACCEPT 创建新的 dwell numeric identity，
   完成由该 timer 负责；安装失败单独保留本地错误和清理状态。

原 SDK 一次处理单个 10-byte 广播参数块，本批仍按该明确布局校验。原 SDK
的 dialog 会重用；当前匹配不等于跨任意 RF 延迟的不可复用 cookie，这仍是
公开 Agreement 接入前必须处理的范围，不能把内部 timer identity 当成 RF
帧携带的身份。原有已审计的 callback-before-recycle 边界仍须阶段运行验证。
