# W-02：保留 Station 资源的已配置 AP 重开

## 2026-09-12 不同配置的共享 AP 激活

当前增量已接通固定 C3/S3/C5 SDK 的不同 AP 配置激活，保留既有 Station/Application
identity、Station helper 和当前 storage。运行/实机/RF 验证仍后置；下方早期“仅匹配
已存配置”的限制已由本增量替代，其他 owner/操作准入条件继续有效。

确认的原生顺序缺陷：wifi_mode_set(APSTA) 会先调用 wifi_create_softap，后者在
C3/C5/S3 的 g_ic+20 发布 AP 接口。wifi_softap_set_config 和
wifi_disable_pmf_config_process 均会在该接口非空时调用 SoftAP start/stop。
因此“创建 AP 后、_do_wifi_start(AP) 前再写配置”仍可能提前广播，不能用它证明
启动前安全读回。已将实际 helper 改为创建前写入；不是仅变更注释或模拟状态机。

当前生产顺序：Radio 精确生命周期准入及法规校验 → 捕获请求/前驱配置 → AP netif
准备 → 同步 Wi-Fi task mode 命令 → 核对原生模式 STA 且 AP 接口为空 → 私有配置入口
→ 必要的 AP-only PMF disable → 全字段/安全读回 → 原生 AP 创建 → 正常 AP_START
与事件 marker。自动信道允许 SDK 规范化；显式信道仍严格核对，返回最终实际主信道。

私有入口由 scripts/prepare_idf_ap_prestart.py 生成，仅调整原生 setter 的模式准入为
STA。三个目标原始 libnet80211.a 和 member 均锁定 hash；本地全局 mutable alias
转换成共享 SDK 全局引用，最终对象只有一个私有导出、没有可写全局段。公共 setter
及共享 SDK 安装均未修改。g_ic+20 只在 Wi-Fi task 读取，从不改写 native pointer。
SDK 同步命令返回前保留独立请求存储，最后 secure-zero 并释放 CONTROL 预算。

配置/readback/PMF 失败在同一原生窗口恢复前驱；若 factory 失败留有接口，拒绝在
该接口上回滚配置，以免回滚触发广播。保留原错误及回滚结果。SDK 退回 STA 后再
确认 AP 接口为空；只有从未允许原生 AP start 的已知配置事务可走无 AP_STOP 的
事件 marker 清理。stopAP 完成 AP 资源退休且 RAM 回滚核验成功后清除本事务故障，
radio.configuration 仍保存失败历史。FLASH 可能写入、未知来源、回滚失败或后续
AP 激活失败均保留故障；不能据此承诺保持连接的任意故障恢复。

test_wifi_ap_reopen_admission.py（2 个方法）、Host C ap-reopen-activation 的

精确 identity、原生失败/读回不符/回滚失败、事件队列失败与未完成后缀。

## 已实现与仍缺的区别

startAP 的冷启动路径继续使用独占 RAM 配置事务。存在 live Station 时，新路径
读取已存 AP 配置，与请求的 SSID/密码、安全要求及 channel/hidden/maxConnections/
beacon/DTIM/CSA/FTM/扩展字段比较；安全字段沿用已存在的强化读回规则。匹配后
只启用该已有配置，不写 config/storage，不 stop/start Station，不替换 Station /
Application lease、helper、IP/queue/timer。新建的 AP lease 使用单调 identity。

固定 SDK esp_wifi.h 明确 set_config 只能用于已启用接口。因此不能在 live STA
上先切 APSTA 再写新配置，否则可能先启用旧配置。本批不实现这种顺序；请求与
已存 AP 不匹配，在任何模式 mutation 前失败，使用已开放的 configure 显式
allowDisconnect 事务更换配置。**保持 Station 连接的不同配置激活仍未完成**，没有
把这项需求改写成“已支持”或“target-unsupported”。

## 原生和 helper 顺序

1. 先纯校验请求、健康 STA mode/live 与精确 Station role/required-mode，再
   一次生命周期准入排除 foreign owner、wake、promiscuous、native operation。
   此时只有 Station/Application；临时 secure calloc 读取 AP 配置。缺少 identity
   容量、分配/SDK 失败或配置不匹配释放该只读 reservation，不释放旧 owner、
   不写 driver、不留下虚假 cleanup。临时完整配置在所有出口 secure-zero/free。
2. 保留同一 token，分配 AP lease；AP helper 记录借用 token，准备 netif、attach
   与 default handlers。JS secrets 只在本次调用栈，不跨回调/重试保留。
3. AP_START 专属事件阶段只期待 AP_START，但要求 live mask 为 APSTA；默认
   event marker/revision 隔离沿用原生实现。模式 setter 只尝试一次；START / fence /
   mode readback 后读取实际信道，再发布完成并把 Application requirement 升为
   APSTA。Station 所在信道可能与输入 AP channel 不同，返回实际 primary channel。
4. 失败后把该 token 和 owner identity 交给现有 AP removal。未尝试模式切换的
   netif setup 可直接退休 AP；只要尝试过切换，就必须完成 AP_STOP/native fence
   才能释放其 netif。无法证明 AP 终止时保留资源，Station 断开/原生操作排空后
   wifi.stop 或 runtime teardown 可接管整体清理。startAP 不重放失败 mutation。
5. AP removal 不清除 ap-reopen-* 激活故障。还原到 STA mode 不代表 driver 恢复，
   必须显式 shutdown 清理；永久 netif detach 错误仍要求设备重启。

boot metadata 复用 AP transition 的三 owner ID，只增加两个 bool；没有多代池或
新预算器。事件 callback 共享 live mask 的读取使用短临界区；SDK/native wait
仅在 operation mutex 下，不置于临界区，也不轮询 JS。

## 契约与诊断

startAP 仍只有原有 options。AP 错误包含 ap-reopen-admission/start 等 stage；
radio fault/cleanupStage 增加 ap-reopen-state/events/mode/mode-readback/channel，
eventPhase 增加 ap-start。注册方法数量保持不变，类型、API 文档和 SDK map 同步。
原 API 文档的“全部凭据仅 RAM”和“不支持 APSTA”陈旧说明也按 configure/storage
与实际 capabilities 修正。API availability 不等于稳定等级或实机连接连续性。

## 2026-09-11：显式授权的 AP 配置切换

当前 `startAP` 增加顶层 `allowDisconnect?: boolean`，默认 false。true 直接进入
既有配置协调器，允许更换运行中 AP 或从 STA 启动不同配置 AP。固定 SDK C3 的
`wifi_softap_set_config` 在写入前检查 AP/APSTA 模式，公共 wrapper 不能对 inactive
AP 预写；`build/w02-ap-live-review` 保存了该路径的反汇编。因此本增量使用明确
授权的 STOP/写入和安全读回/START，不把它描述为 Station 连续连接方案，也不修改 SDK。

内部 `activate_ap` 只由此入口构造，不能由公共 configure 输入或 start-only 入口
传入。当前 mode/storage 的解析、AP mode 增加和 lifecycle token 准入在同一 Radio
mutex 内。冷启动默认 AP/RAM，已有 STA 变为 APSTA，原 AP/APSTA 保持其接口集合；
保留已存 Station 配置与 storage（FLASH 下新 AP 凭据会按该策略保存）。原连接明确
断开，不自动重连；helper/IP/lease 经过标准退休和重建，不承诺身份保持。

权限不能绕过精确 owner、native operation、pending Future、wake 或清理故障准入。
输入、GC rooting、凭据擦除和 AP 安全验证共用原 parser；捕获失败不返回 true 权限。
原执行器负责断连 drain、STOP/fence、helper 退休、配置 rollback/readback 和 START；
失败只保留中央清理后缀，不保留 JS 输入，不自动重发。错误阶段由既有 AP/Radio
诊断提供；结果转换 OOM 后应先检查 status。默认路径仍要求原 AP 先 stopAP，并仅
允许匹配配置的共享重开；明确 true 的同配置请求仍会执行停机事务。

更新的 fixture 调用生产 parser/adapter/Radio selector/执行器，覆盖权限类型与
GC/OOM、同锁 mode/storage 选择、错误组合、foreign owner/native busy、中央失败
后缀及禁止重复提交。当前仅 AST，不导入/编译/执行这些 fixture；生产定向语法和
manifest 结果见 `build/w02-ap-activation-evidence.json`。真实断连、APSTA 重建、持久化
异常和 RF 全部 not-run；保持 Station 连接的新 AP 配置激活继续为独立缺口。
