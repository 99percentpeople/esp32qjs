# W-08 广播 setup 响应 / dwell 定时器

广播 TWT 的两个原生 timer process 已接入数字身份适配，作为广播 Agreement
建立/关闭的前置生命周期工作。尚未注册 setupBroadcast；TX/RX 关联、结果
控制、owner 和完整联合回收仍待接入。上批 broadcasts() 查询保持不变。

## 固定 SDK 证据

SDK 为 `fff9895c82`，C5 `ieee80211_btwt.o`：

- `btwt_setup_timer` 为 1248 B：32 个 20 B ETSTimer、32 个 uint16 timeout、
  32 个 17 B 参数槽，起点分别为 0、640、704。
- TX 成功 callback 在 `+0x98` 复制参数，安装响应 timer；收到接受响应后
  `ieee80211_process_btwt_setup_action` disarm/done，再安装 dwell timer。
- 原响应 / dwell callback 将参数槽地址分别投递到 native operation 30/31；
  消费时会读取这个可复用地址。响应超时删除 timer，dwell 不删除其 handle。
- dwell 在 `+0x136` 检查 PS，NONE 时 `+0x13c` 调用 pm_set_sleep_type(1)；
  `+0x156` 使用 32 位 shift，`+0x186` 将结果符号扩展给后续 64 位接口。
  原生 duration 固定乘 256，未处理其他单位。
- `cnx_sta_pm(false, ...)` 在 `+0x10` 调用 close_all_twt_sessions；原 close
  清理协议位图/PM 状态，未退休上述广播 timer。

这些是固定归档的静态调用链证据，未写成已执行竞争复现或实机通过。

## 生产适配

现有 OSI setfn/disarm/done/arm 路由识别广播表的精确 timer 地址。仅第一次
使用时分配 32×36 B INTERNAL 记录；条目保存 node 地址值、17 B 参数副本、
不回绕 numeric identity、phase、错误和 active/fired/busy/stopped 状态。
callback 与 native queue 只携带数字，不借用 SDK 参数槽或 JS/Future 对象。

消费时核对当前关联、同一 node、同一参数槽内容、phase 和 broadcast ID，
然后向原处理器传入本次局部副本。dwell 在 mutation 前复核显式 PS 策略、
非零 duration、256 us 单位及可由原生 signed 32-bit 算术表示的正 interval；
并核对原生 AP 表存在。不把截断后的间隔当成已接受的正确配置。

disarm 先撤销 callback 权限；stop 失败保留 handle，不跳到 delete。delete
失败只重试 delete 后缀。错误保留最早阶段和当前清理状态；未知 handle
不会被当作本次 owner 删除。native process 返回后补齐 dwell 遗留的 timer
清理。精确 cancel 拒绝旧 token，busy process 保留直到返回。

close_all 包装先撤销全部广播 callback，再逐项尝试清理并进入原生 close。
已排队的旧数字在重连后仍不能重新激活。清理错误不重试 RF，不以 runtime
restart 冒充物理恢复；完整生命周期仍需后续 owner/恢复器协调和阶段验证。

内部 SDK 快照新增 broadcast_timer 的资源、active/fired/busy/fault/cleanup
位图及原始错误。广播 setup wrapper 在已有 timer 故障时拒绝新请求；此
wrapper 的公开调用链须随 setupBroadcast 接入后再验，不把 archive 中的
代码等同于当前可调用 API。无新的正式 JS 类型或占位接口。
