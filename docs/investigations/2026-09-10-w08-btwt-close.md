# W-08 广播 teardown 联合回收

本批将已完成 teardown 纳入已有广播 setup 回收协调器：保存关闭结果，确认
TX/recycler/PM 静止，串联 timer/native/event 顺序，最后释放原生 teardown
记录和 setup held。公开 Radio/Agreement/Future 接入仍未完成；协调器自身
不发送关闭帧，也不把重试清理解释为重新提交 teardown。

## 准入与关闭结果

Pending setup 沿用原有取消路径。存在精确广播 teardown 记录时，按 request
identity、广播 ID 和类型核对，要求原生提交及 callback 已结束、输出返回且
buffer 已回收，必要时在原生任务归还残留 PM 引用。SDK bitmap 仍表明协议
已建立时，不允许取消 setup。

资源静止后继续核对关闭结果：提交错误保留原值，completion 错误/含糊状态
保留，未收到确定结果为 NOT_FINISHED，发送失败为 ESP_FAIL。只有成功完成
或原连接已经通过真实 close-all 路径撤销，才允许继续退休。队列观察错误
单独保存，不阻止已经完成的原生关闭。原连接撤销也不能绕过 TX/recycler
未完成、tracking fault 或未知资源状态。

失败路径不自动发第二个 RF 请求，不清除关联 owner，不恢复别的连接。失败
后显式重试/物理恢复的公开策略还须随 Agreement 接入完成；未知完成仍保留
可诊断占用，不能把其超时标记为成功关闭。

## 顺序与失败后缀

静止 cut 新增 teardown revision，与 TX revision、timer revision 一起检查。
worker 等待 TASK timer callback 实际退出/删除，再经过 native queue marker，
最后向 boot Radio handler 发布 copied-number marker；无 runtime/Future 指针。
任一 revision 变化都会清掉旧 marker，重新取得静止 cut 并确认顺序。

最终 native release 重新核对完整 cut 和事件确认，在 timer lock 外释放精确
teardown 单例，再复核 timer 状态后撤销 setup held。若两次释放之间出现新
状态，setup 仍保持 held，下一次以新的 cut 继续，不能提前复用。held 加上
cancel_requested 阻止同一请求在中间重新提交关闭。

协调器在清理前和最终 release 前保存精确 teardown 值快照；单例释放后也保留
submit/completion/observation 结果，供 owner/Future 交付。重复 poll 只执行
尚未完成的 marker 清理后缀，不再取消、重发或释放别的请求。

## 内存与静态验证

cut 从 8 B 增至 12 B，copied event 从 20 B 增至 24 B。协调器保存既有
40 B teardown 快照，按 C5 的 8-byte 对齐，稳定 owner 记录从 96 B 增至
144 B（+48 B），已核对实际 DWARF；它尚待公开 owner 分配，
没有新增静态池。teardown 静态对象仍 56 B，timer 静态对象仍 52 B，广播
延迟 timer 池仍 3328 B，TX 账本和可选存储不变。

通过；manifest/feature/schema/coverage、严格 TypeScript、MQuickJS 语法检查
通过。证据为 `build/w08-btwt-close-evidence.json`。SDK patch 与上一批完全相同，
