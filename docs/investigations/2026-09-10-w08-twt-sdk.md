## 本地 SDK 证据

重新核对 C5 `libnet80211.a` 的 `ieee80211_twt.o`、`ieee80211_btwt.o`、
`ieee80211_ioctl.o`、`ieee80211_api.o`，以及源码 `ets_timer_legacy.c`、
`esp_timer.c`、C5 adapter 和 ETSTimer 声明。原始 archive SHA-256：
`4c86fc1d2f40a933af7f672972978eb7c82651d838fd10584e006438d585793b`。
既有 build-local archive gate 同时约束本 adapter；未修改共享 SDK。

| 原生字段 | 固定 C5 布局/含义 | 静态证据 |
| --- | --- | --- |
| `setup_timer_param` | 372 bytes；8×17 request bytes、8 dialog bytes、8×20 ETSTimer、8×uint16 timeout、8×int16 ID、8 opaque words、pending bitmap | symbol size；setup、response、timeout、stop handler 的读写偏移 |
| pending bitmap | offset 368，与已建立 flow 位图分开 | setup 在 offset 0x1b4 读取，0x1bc 调用 first-free；slot 未另做 `<8` 检查 |
| pending ID | offset 320+2×slot，仅 occupied slot 有效 | setup 写入、timeout event 和 ID-existence check 读取 |
| pending flow | 每份 17-byte request 的 byte3 bit7 + byte4 bits0..1 | setup event poster 的 flow 解码，与 request builder 一致 |
| `s_itwt_id` / `s_tmp_itwt_id` | 各 8×int16，初始 -1；独立于 pending ID | symbol/section 与 `is_twt_id_exist` 的三处检查 |
| `btwt_setup_timer` | 1248 bytes，前 32×20 bytes 是 ETSTimer | symbol size 与 setup TX callback 按 ID×20 调用 timer setter |
| ETSTimer | C5 sizeof 20，timer_arg offset16 | SDK 声明 + production static assertions；legacy 实现把 timer_arg 用作 esp_timer handle |

静态确认的准入缺口：

- 公开 iTWT wrapper 检查已建立 flow 是否满；native setup 再从独立 pending
  bitmap 查找空 slot，却没有在八个 pending slot 全占时拒绝。此时 first-free
  得到 slot 8，后续 request/timer/ID 索引超出相应数组分区。
- native flow 选择只考虑已建立位图，没有考虑其他 pending request 的 flow。
  多个 setup 可覆盖同 flow 的临时 ID/timeout；SDK 的外层 ID 检查也没有覆盖
  从 API 检查到 native mutation 之间的排队窗口。
- bTWT wrapper/handler 在按 ID 查询 AP 32 项表前缺少范围校验。上轮 JS 输入
  校验已防止该入口传入越界值，本轮把保护推进到 native public-API handler。

以上来自固定二进制控制流，不是 RF/并发运行复现；相关运行用例按用户安排后置。

## 实现

新增 `wifi_twt_sdk.h/.c`，受 Wi-Fi + HE gate 控制；私有表布局及 setup wrapping
仅在已审查 C5 下启用。其他 HE target 的内部 snapshot 返回 NOT_SUPPORTED，
不把此实现限制冒充芯片没有 TWT。

`esp32_mquickjs_wifi_twt_sdk_snapshot()` 复用现有 Action 原生 ioctl adapter 的
独立 sentinel 分支；只有框架专用 callback identity 能进入。实际读取在 Wi-Fi
任务内完成，不进行 RF、mode、power-save 或隐式 start。读取结果全为有界值，
没有 timer/SDK 指针外泄；SDK dispatch 失败时不部分提交输出。

快照包括 iTWT 已建立/pending/suspend/resume 位图、三组 ID、pending flow、
setup/information/probe timer handle presence，以及 bTWT 原生 ID 位图和 32 位
setup timer presence。空 pending slot 的 ID/flow 分别标为 -1/255，不把旧表
内容当作活动请求。timer bit **只表示句柄存在，不表示 armed 或 callback 已退出**。

两个 setup native handler wrapper 在实际 mutation task 中执行：

1. 参数预验证复用 production TWT validator；无效输入不进入原 handler。
2. iTWT 在 pending 表满、已建立+pending flow 全占时返回 `ESP_ERR_WIFI_TWT_FULL`。
   同一原生任务内重查三组 ID，重复 ID 返回 INVALID_ARG。
3. 原偏好 flow 被占用时，在已建立+pending 的联合位图中选择空 flow，再交给
   SDK 原 handler；保留原生 in/out 写回语义和后续 SDK 原始返回值。
4. bTWT ID 必须在 1..31，防止进入未经边界检查的 AP 表索引。SDK 的连接和
   AP 能力检查继续由原 handler 执行。

这不是完整 native admission：Radio owner、连接代次、HE/power-save 共存、
同请求的未来回调身份和 timer/发送退休仍须接入。当前 JS 尚无 setup 调用者，
生产链接会丢弃两个 setup wrapper 和外层 snapshot 调用函数；native snapshot
本体因 ioctl 分支可达而链接。不能把对象已编译、link options 已存在说成
两个 setup wrapper 已在当前镜像中执行；最终 SDK→wrapper 链接还须在公共
setup 接入时再次核验。

## 退休边界为何仍未完成

`ets_timer_done()` 调用异步 `esp_timer_delete()` 后立即清空 timer_arg；
`esp_timer.c` 明确允许停止后 callback 仍在运行，并把删除交给 timer task。
因此“句柄为空”不能证明旧 callback 不再引用原 slot。TWT timer callback
还会经 `ieee80211_timer_process` 把工作转交 Wi-Fi task；两队列之间也要排空。

下一步需完成实际 timer-callback/SDK TX 退休与精确 Wi-Fi/event-loop 排空，
再把证明交给上一轮的记录；不得由空 bitmap、断连标志或 elapsed timeout
直接调用 `sdk_retired`。无 cookie 的 teardown 重试和 RF dialog token 复用
歧义继续保留，不用这两个 setup guard 声称已解决。
