# Raw TX 自定义源地址：接收证据与完成状态

## 范围

在本地两块自有开发板之间使用带唯一标记的 Probe Request 和测试用
vendor Action 帧验证完成状态。没有发送 deauthentication/disassociation，
没有访问第三方目标，没有修改接口 MAC、固件或工作区文件。

- C5：`hw-10bda3c854e8`，bootId `712f0c74eb2d90b0`。
- S3：`hw-e8f60a8bbdc0`，bootId `e27d579a675039cd`。
- 两端均未关联，信道 6，Station 接口，driver sequence。
- Addr2 对照：发送接口实际 MAC / 本次测试专用局部地址。
- Addr1 对照：广播 / 另一块开发板的实际 Station MAC。
- 接收过滤同时包含两种源地址；按原始帧字节中的测试编号匹配。

## 已确认结果

C5 发送、S3 接收的 Action 三轮对照：

| Addr2 | Addr1 | rawStatus | S3 匹配接收 | SDK 提交至完成 |
| --- | --- | --- | --- | --- |
| 本机 | 广播 | 0，3/3 | 3/3 | 1.065–11.991 ms |
| 本机 | S3 | 0，3/3 | 3/3 | 1.858–6.704 ms |
| 自定义 | 广播 | 0，3/3 | 3/3 | 1.055–1.229 ms |
| 自定义 | S3 | 1，3/3 | **3/3** | 149.644–341.359 ms |

Probe Request 的完整字节对照同样四组均接收；自定义源地址单播的
`rawStatus=1`，SDK 完成耗时 183.890 ms。接收数据保留自定义 Addr2，
排除了框架或 SDK 在该路径上悄悄替换源地址的解释。

交换板角色时，S3 的四组 Action 均成功且被 C5 接收。但是 S3 发送时
原有 Monitor 仍开启，不能将这一结果单独归因为 MCU 差异。

发送端接收监听的受控开关对照改变了 C5 完成结果，并在成功用例中
记录了对应的 ACK。恢复原接收状态后，相同自定义源地址单播再次失败
（127.223 ms），S3 仍收到原始帧。接收模式影响 ACK 接收／完成的解释
得到支持，但尚未证明具体硬件过滤位、SDK 分支、重试计数或超时来源。

## 诊断结论与限制

这次实测推翻了“Addr2 不匹配就不会发射”的普遍解释，也不支持
“Addr1 必须在发送接口关联表”的解释。`WIFI_SEND_FAIL` 与对端接收
不是互斥事件；不能将完成失败重映射为发送前拒绝或强制改为成功。

没有独立第三方接收器记录默认接收模式下的 ACK，因此不能断言该模式
下对端未发 ACK。Monitor 不是完全被动的观测手段：启用它会改变发送端
接收状态，其副作用必须作为实验变量，而不能直接当作固件修复。

本次没有实现驱动绕过补丁，没有做其他帧类型的 RF 资格验证。

## 证据与测试工具修正

本机原始请求、返回和可复核匹配结果保存在
`build/raw-tx-sa-investigation/verification.json` 及同目录各次
`send-*.json`、`receive-*.json`。28 个完整字节用例逐一匹配通过。
目录是忽略的本机调查输出，不随 Git 提交。

两次前期采样的接收输出分别受工具 16 KiB 上限、ByteView JSON 序列化
影响，不能作为逐帧字节证据。后续使用 `frame.bytes().toArray()`，
显式关闭 View 和 Frame，并仅返回必要字段，解决采样工具的问题。
一次主机脚本变量覆盖影响了 ACK 接收收尾；随后读取原会话完成记录，
显式关闭并校验状态，未重复提交那次发送。

测试后两块板 bootId 均未变化、启动状态 healthy、Raw TX 无活动操作或
待清理工作；C5 Monitor owner 恢复为 0，S3 恢复为测试前的 1。
所有本次创建的会话与定时器已释放，S3 原有 Monitor 保留。

## 后续正常源地址回归

按正常通信范围继续检查：使用发送接口实际 MAC，Addr1 指向另一块自有
开发板；只发送带测试标记的 Action 帧。两端保持信道 6、未关联状态，
没有修改接口地址或发送侧接收策略。

- 33、300、1000 字节，各自覆盖 driver/application 序号并重复两次。
- C5 → S3：12/12 成功且逐帧匹配接收，SDK 完成耗时 1.470–12.729 ms。
- S3 → C5：12/12 成功且逐帧匹配接收，SDK 完成耗时 1.012–38.380 ms。
- 接收保留前 64 字节，通过帧头和标记确认；不声称验证完整载荷或 FCS。
- 本轮没有复现 150 ms 左右失败、完成关联故障、隔离或 native 清理滞留。
- 两块板 bootId、各 Radio client 数量与测试前一致，启动状态正常。

本地生产 `wifi_raw_tx_snapshot.c` 将 SDK success/fail 原值转换为
对应完成状态，未发现把源地址不匹配自行转为 failed 的逻辑。快照与
broker 现有 native 回归覆盖回调边界和所有权回收；这类主机验证不能
证明无线 ACK 或特定芯片内部重试路径。

原始发送、接收、前后状态及匹配断言保存在本机忽略目录
`build/raw-tx-normal-regression/`。本轮没有新增驱动补丁或刷机；正常
源地址的短程回归通过不等于全部帧类型、关联模式和长时间稳定性合格。
