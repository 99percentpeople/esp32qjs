# C5 runtime buffer SRAM reduction

## Scope and allocation policy

The 2026-09-07 change keeps the RPC wire format, four decoder slots, 64 log
entries, 512-byte log text limit and read limits unchanged. It moves storage
out of statically reserved internal RAM:

- Each live RPC decoder owns one `rpc.decoder` payload, allocated on creation
  and freed on explicit close, object finalization or runtime cleanup. Reset
  reuses the allocation. The slot, generation and file-stream control remain
  internal. Allocation failure does not consume a slot or codec reference.
- The runtime owns one `runtime.logs` payload for the ring. Initialization
  allocates before installing the ESP-IDF log callback. Shutdown detaches the
  ring under the permanent internal lock, then frees it outside the lock.
  An in-flight callback checks active state and ring pointer under the same
  lock. Restart never reinitializes a lock another task may still reference.
- Log reads use a temporary `runtime.logs.read` payload and release it on both
  successful JS conversion and exception paths.

All three use the existing `MEMORY_EXTERNAL` policy: PSRAM when present;
reserve-checked internal RAM on devices without PSRAM. When an enabled PSRAM
heap is exhausted, this class reports allocation failure instead of spilling
into scarce internal RAM. The memory manager reports owner, region and bytes.
Generation-wide movable-block cleanup does not own these fixed payloads;
their explicit lifecycle cleanup remains necessary.

These buffers are accessed from ordinary task context. The existing normal
ESP-IDF log callback is not an ISR/cache-disabled logging interface. Early and
DRAM logging use the SDK's constrained logging path. No task stack, DMA buffer,
ISR buffer, or general BSS placement is changed. See the
[ESP-IDF log documentation](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32c5/api-reference/system/log.html)
and [external RAM restrictions](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c5/api-guides/external-ram.html).

## Linked C5 result

Target: XIAO ESP32-C5 revision 1.0, hardware ID `hw-10bda3c854e8`, 8 MiB flash,
8 MiB quad PSRAM. ESP-IDF v6.1 checkout `fff9895c82`.

| Internal symbol | Before (bytes) | After (bytes) |
| --- | ---: | ---: |
| `s_rpc_decoders` | 31,936 | 800 |
| `s_runtime_logs` | 34,356 | 556 |
| Total | 66,292 | 1,356 |

These two symbols release 64,936 bytes (63.4 KiB) of internal static storage.
This is a linked-symbol measurement, not a prediction that every byte becomes
free heap: runtime and SDK allocation placement may change with available RAM.

The deployed agent normally has one decoder, requiring 7,784 bytes of PSRAM,
and the log ring requires 33,804 bytes. Log-read snapshots temporarily require
up to 8,448 bytes, plus allocation metadata.

## Hardware deployment and validation

The pre-flash read verified the same C5 hardware ID, chip, flash and PSRAM.
Boot ID was `ec0d24bf290e04ab`, runtime healthy, no safe mode, zero startup
failures. Internal free heap was 44,827 bytes, largest block 22,528 bytes;
PSRAM free was 4,078,720 bytes. The DMA capability heap overlaps internal RAM
and must not be added to it.

Preserve flash job `bf4c4e446f206087940a76ec` entered C5 ROM automatically and
verified hashes of every written image. The 4,653,056-byte workspace at
`0x390000` was preserved. Watchdog reset then lost the Windows browser serial
endpoint. The job ended with `BROWSER_SERIAL_RECONNECT_TIMEOUT`; no endpoint
or Agent was available afterward. **Bytes verified does not establish a
successful application boot.** No blind flash/reset retry was performed.

After the user reconnected the browser, read-only identity verification found
same hardware ID, C5 revision, flash and quad PSRAM profile. Boot ID was
`fa2bebe3c27bf19a`; its reset reason was `power-on`. Runtime startup was healthy,
with no safe mode and no startup failures. Thus application recovery is now
confirmed after user reconnection; this does **not** turn the earlier automatic
browser reconnect failure into a successful automatic-reset test.

The reconnect sample shows 64,952 bytes (63.4 KiB) more free internal SRAM.
The log ring (33,804 bytes) and one decoder (7,784 bytes) are both reported in
PSRAM. Temporary log snapshots leave no owner allocation after reads. Small
internal-heap differences between samples are normal runtime activity.

The added `rpc/memory` and `sys/runtime-log-memory` callbacks ran on the device
through bounded, synchronous operator exec calls with assertion shims. Both
passed: 20 decoder create/decode/reset/close cycles, codec-orphan lifetime,
GC cleanup, UTF-8 console capture, and 20 log snapshot reads. The existing full
`rpc/offline` suite was not run on this production image. The original combined
test request exceeded the 4,096-character exec limit and was rejected before
dispatch; RPC memory coverage was split into its own registered test case.

Two explicit `sys.restartRuntime({reason:"sram-regression",delayMs:200})`
requests were acknowledged. The boot ID stayed unchanged and generation
advanced 1 -> 2 -> 3. After both restarts, PSRAM free stayed exactly 4,037,068
bytes and managed payloads stayed at 152,397 bytes, with one log ring and one
Agent decoder. Both device memory tests passed again in generation 3 (another
20 decoder cycles and 20 log reads). No retained allocation from the previous
runtime generation was observed for these buffers.

Final startup was healthy, safe mode false, failure count zero and memory
pressure normal. Final internal free heap was 109,895 bytes (107.3 KiB), with
59,392 bytes (58 KiB) in the largest block. A sample during restart recovery
had 101,835 free bytes, which recovered after subsequent requests; the largest
block remained 4 KiB smaller than the initial post-flash sample. No persistent
increase in allocated internal bytes was observed in the final sample. These
bounded checks do not establish long-duration fragmentation or soak behavior.

Runtime restart and memory-manager Python checks passed 8/8 and 10/10. The
updated RPC test registry includes both offline and memory cases. C firmware
sources are unchanged from the flashed artifact; only test organization and
this evidence record changed after the build. No new frontend build, flash,
