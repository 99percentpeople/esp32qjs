## 固定 SDK 问题与处理顺序

固定 C5 SDK `fff9895c82` 的 `btwt_setup_dwell_timeout_fn_process` 在 +0x17a
发布 WIFI_EVENT_BTWT_SETUP，随后才在 +0x1ac 调用 pm_start_twt、+0x1c4 调用
更新 inactive time 的 helper，之后写 interval table。原 wifi_event_post
等待观察队列；仅在事件发布处保存成功并不能证明后面的原生写入已经完成。
这是归档反汇编确认的顺序，未作为运行竞争复现或 RF 验收。

生产 timer process 在匹配当前关联、参数副本和不可复用 numeric identity
后进入同步 capture scope。原 SDK setup 事件在该 scope 内复制，不入观察
队列；原处理器返回后退出 scope，完成 timer stop/delete 后缀的一次尝试，
在同一精确 timer entry 保存终态，最后零等待发布观察事件。

结果保留归一化事件、identity、seen/complete/ambiguous、native_error 和
observation_error。complete 表示本次原生执行结束且清理已尝试，不表示
资源已全部释放：失败的 stop/delete 仍保留 handle，后续只重试未完成后缀。
最早原生/清理错误与观察队列错误独立，观察失败不把已完成原生执行重新
变成 pending。发布期间 pin 同一 entry，不能替换或取消释放该结果。

值读取按 slot + 不复用 identity 校验，错误 identity 不改输出。该 reader
目前在生产 object/archive 内，尚无公开 Agreement caller，不将其存在写成
公开生命周期完成。后续 owner 必须在允许 slot 替换前取得本次结果。

## 事件边界

WIFI_EVENT_BTWT_SETUP/TEARDOWN 进入同一个生产 wrapper，其他事件沿原路径。
按 SDK 状态复制定义字段，清零 padding 与无效字段，不交付原生栈垃圾。
SUCCESS 校验 command、duration、interval、trigger/flow；重复的同值事件
不重复完成，冲突结果保留首个值并报告 ambiguous。缺失/无效事件成为本地
控制错误，不伪装成 AP 超时或 RF 失败。

scope 仅保存同步调用期间的栈地址，按同一 task 和严格栈顺序进入/退出，
不进入 callback/Future/JS root。其他 task、其他 ID、其他种类的有效事件
只作零等待观察，不按 broadcast ID 猜测 owner。当前 scope 收到同种类但
无法合法解析的 payload 时记录控制错误；不从不合法字段推断请求身份。

没有 scope 的 TXFAIL、RX 拒绝和 teardown 观察也不阻塞 Wi-Fi task，但它们
尚无托管 owner 终态，仍须后续 TX/RX 关联和 teardown 生命周期接入。
