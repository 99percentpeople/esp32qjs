# Repository Guidelines

## Project Structure
This is an ESP-IDF firmware project with board-specific profiles for multiple ESP32 targets. Application bootstrap now lives in [`main/`](</home/zach/esp32qjs/main>): [`main/app_main.c`](/home/zach/esp32qjs/main/app_main.c) allocates the JS heap, creates the runtime, mounts LittleFS, and binds the JS backend to the interaction component through generic callbacks. App-level resource tuning, including JS heap sizing, LittleFS formatting, and the top-level `ESP32QJS_ENABLE_REPL` product switch, lives in [`main/Kconfig.projbuild`](/home/zach/esp32qjs/main/Kconfig.projbuild). The ESP32 adapter and embedded JS engine live under [`components/esp32_mquickjs/`](</home/zach/esp32qjs/components/esp32_mquickjs>): the current public header entrypoint is [`include/esp32_mquickjs.h`](/home/zach/esp32qjs/components/esp32_mquickjs/include/esp32_mquickjs.h), internal binding headers are under [`internal/`](</home/zach/esp32qjs/components/esp32_mquickjs/internal>), core runtime glue under [`src/core/`](</home/zach/esp32qjs/components/esp32_mquickjs/src/core>), and feature modules under [`src/modules/`](</home/zach/esp32qjs/components/esp32_mquickjs/src/modules>). For example, [`src/core/esp32_mquickjs.c`](/home/zach/esp32qjs/components/esp32_mquickjs/src/core/esp32_mquickjs.c) owns runtime setup and global registration, while [`src/modules/fs/esp32_mquickjs_fs.c`](/home/zach/esp32qjs/components/esp32_mquickjs/src/modules/fs/esp32_mquickjs_fs.c), [`src/modules/gpio/esp32_mquickjs_gpio.c`](/home/zach/esp32qjs/components/esp32_mquickjs/src/modules/gpio/esp32_mquickjs_gpio.c), [`src/core/esp32_mquickjs_esp32.c`](/home/zach/esp32qjs/components/esp32_mquickjs/src/core/esp32_mquickjs_esp32.c), and [`src/modules/wifi/esp32_mquickjs_wifi.c`](/home/zach/esp32qjs/components/esp32_mquickjs/src/modules/wifi/esp32_mquickjs_wifi.c) hold runtime and module-specific host APIs. Serial REPL, line editing, prompt redraw, and log/console bridging now live in the generic interaction shell [`components/esp32qjs_interactive/`](</home/zach/esp32qjs/components/esp32qjs_interactive>): the public entrypoint is [`include/esp32qjs_interactive.h`](/home/zach/esp32qjs/components/esp32qjs_interactive/include/esp32qjs_interactive.h), internal REPL headers are under [`internal/`](</home/zach/esp32qjs/components/esp32qjs_interactive/internal>), and runtime plus REPL sources are under [`src/`](</home/zach/esp32qjs/components/esp32qjs_interactive/src>). That component no longer depends on `esp32_mquickjs` types directly; any backend, including the current JS runtime, is expected to implement the callback interface from `main`. Component defaults for board pins, timeouts, timers, and HTTP capture limits live in [`components/esp32_mquickjs/Kconfig.projbuild`](/home/zach/esp32qjs/components/esp32_mquickjs/Kconfig.projbuild), while interaction-specific tuning such as display width and `/littlefs/index.js` autorun now lives in [`components/esp32qjs_interactive/Kconfig.projbuild`](/home/zach/esp32qjs/components/esp32qjs_interactive/Kconfig.projbuild). Board-specific remote/build profiles live under [`configs/boards/<board>/`](</home/zach/esp32qjs/configs/boards>) and each board directory carries its own `.env`, `sdkconfig.defaults`, and `partitions.csv`. Automated host C tests live under [`tests/c/`](</home/zach/esp32qjs/tests/c>) and board-backed JS test assets live under [`tests/js/`](</home/zach/esp32qjs/tests/js>). Upstream `mquickjs` source stays in the submodule [`components/esp32_mquickjs/vendor/mquickjs`](</home/zach/esp32qjs/components/esp32_mquickjs/vendor/mquickjs>), and committed generated headers live under [`components/esp32_mquickjs/generated/`](</home/zach/esp32qjs/components/esp32_mquickjs/generated>). Top-level [CMakeLists.txt](/home/zach/esp32qjs/CMakeLists.txt) owns project setup, [`sdkconfig`](/home/zach/esp32qjs/sdkconfig) is the committed default configuration, and `build/` plus other board-specific build directories are generated output.

## Build, Flash, and Debug Commands
Run from the repository root after exporting ESP-IDF:

- `git submodule update --init --recursive` fetches the upstream engine source.
- `idf.py build` builds the firmware.
- `idf.py menuconfig` adjusts app/runtime defaults such as JS heap size and placement, REPL width, LittleFS mount/autorun behavior, LED pin, and HTTP response cap.
- `idf.py flash monitor` is the standard local edit-build-run loop.
- `idf.py -p COM3 flash` flashes a directly attached device.
- `idf.py -p COM3 monitor` opens the `USB Serial/JTAG` REPL locally at `115200`.
- `uv sync` provisions the repo-local Python tooling, including `esptool`.
- `cp .env.example .env` seeds the per-repo remote tooling defaults; set `BOARD` and `IDF_PATH` for the local setup.
- `python scripts/remote.py boards` lists bundled board profiles.
- `python scripts/remote.py show-config` prints the merged board/tool configuration.
- `python scripts/remote.py --assume y|n build` skips interactive prompts by answering yes/no automatically.
- `python scripts/remote.py chip-id` verifies the remote RFC2217 link for the selected board profile.
- `python scripts/remote.py flash` builds and flashes the selected remote board.
- `python scripts/remote.py flash-fs` rebuilds and flashes only the LittleFS `storage` partition for JavaScript-only changes.
- `python scripts/remote.py monitor` opens the remote serial monitor without retyping host and tool paths.
- `python scripts/remote.py test` runs the default host C tests plus the JS modules enabled by the active board's runtime feature set, with offline-only network behavior.
- `python scripts/remote.py test --scope c` runs only the host C tests.
- `python scripts/remote.py test --scope js --module fs --module stream --no-flash-fs` reruns only selected JS modules against an already flashed test image.
- `python scripts/remote.py test --scope js --module wifi --module http --network` enables network-required `wifi` / `http` cases when `TEST_WIFI_SSID`, `TEST_WIFI_PASSWORD`, and `TEST_HTTP_URL` are configured.
- `python scripts/remote.py --board esp32c3_supermini build` switches to another board profile without editing `/.env`.
- `idf.py build` now regenerates and syncs the `mquickjs` generated headers automatically when upstream sources change or the generated files are missing.
- `cmake --build build --target update_mquickjs_headers` is still available as an explicit manual refresh target.

Remote flashing setup is documented in [docs/remote-rfc2217.md](/home/zach/esp32qjs/docs/remote-rfc2217.md).

## Coding Style
Use 4-space indentation and standard ESP-IDF C style. Prefer `snake_case` for functions and locals, `UPPER_SNAKE_CASE` for macros, and keep ESP32-specific code in the adapter layer instead of editing the submodule directly. Match existing logging and error-handling patterns with `ESP_LOG*`, `ESP_ERROR_CHECK`, and thin adapter helpers around third-party code.

## Testing
Every code change should pass `idf.py build`. The default automated baseline is `python scripts/remote.py test`, which runs host C tests plus the JS modules enabled by the active board's runtime feature set, with network-required `wifi` / `http` cases gated behind `--network`. That default JS baseline covers the built-in offline runtime APIs across `core`, `esp32`, `gpio`, `ledc`, `adc`, `dac`, `i2c`, `timers`, `fs`, `stream`, `load`, `wifi`, `http`, and `http_server`; modules disabled by `esp32.info().features` are auto-skipped, and explicitly requested disabled modules fail fast instead of being skipped silently. App-level LittleFS helpers such as `display` and `ui` still need separate validation when they change. JS REPL changes should still be spot-checked interactively over serial when behavior is terminal-facing, for example `help()`, `sleep(20)`, `esp32.info()`, `gpio.led(true)`, `ledc.timerConfig(0, { freqHz: 5000, dutyResolution: 8 })`, `JSON.stringify(adc.ioToChannel(0))`, `JSON.stringify(wifi.status())`, `wifi.scan()`, `wifi.scan(function(results, error) { print(error === undefined, results.length); })`, `fetch("http://example.com")`, `fetch("https://example.com", function(response, error) { print(error === undefined, response.status); })`, `setTimeout(function() { print("once"); }, 200)`, `setInterval(function() { print("tick"); }, 150)`, and core file operations such as `fs.writeText("tmp.txt", "ok")`, `fs.readText("tmp.txt")`, and `fs.remove("tmp.txt")`. If `/littlefs/index.js` exists, also validate that it auto-runs before the first prompt. If Wi-Fi credentials are available, also validate `wifi.connect("ssid", "password")` and `wifi.disconnect()`. The canonical API reference now lives in [docs/api.md](/home/zach/esp32qjs/docs/api.md), [docs/c-api.md](/home/zach/esp32qjs/docs/c-api.md), and [docs/js-api.md](/home/zach/esp32qjs/docs/js-api.md). For editor changes, validate multiline continuation as well: typing `(1 +` then Enter should switch to the `... ` prompt, and pressing Enter before a closing `)` should insert a newline instead of submitting. When adding more features, introduce component-level tests or a `test/` directory rather than mixing test code into `app_main()`.

## Commits and Pull Requests
Use short imperative commit messages, for example `Add remote RFC2217 flash helper` or `Split LED init from app_main`. Keep pull requests narrowly scoped, describe the hardware used for validation, include the exact flash or monitor commands you ran, and attach boot logs for behavior changes.
